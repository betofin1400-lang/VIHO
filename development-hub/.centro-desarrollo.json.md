# El marcador `.centro-desarrollo.json`, clave por clave

> **Por qué existe este archivo aparte.** JSON no admite comentarios, y el marcador es la pieza sin
> la cual nada del centro funciona: si sus claves se documentan solo en una guía externa, el día que
> alguien copie el centro a otro proyecto va a rellenarlo adivinando. Este `.md` vive **al lado** del
> marcador y se versiona con él. Cuando cambie el esquema, se actualizan los dos en el mismo commit.
>
> **Qué NO va aquí:** los valores concretos del proyecto (eso es el JSON) ni la política de trabajo
> (eso es `.claude/config-proyecto.md`).

---

## 0. Qué resuelve el marcador

Dos incógnitas que ninguna skill puede adivinar:

- **`<HUB>`** = la carpeta que **contiene** este archivo. Todas las rutas internas del centro son
  relativas a ella, y por eso el centro se puede **renombrar y mover** sin tocar una sola skill.
- **`<ROOT>`** = la raíz desde la que se llega al código, resolviendo `codigo.root_rel` desde `<HUB>`.

**El algoritmo de descubrimiento** (idéntico en toda skill y en todo script; implementado una sola
vez en `.claude/skills/_lib/centro_lib.py`):

```
1. Desde el directorio de trabajo, subir por los ancestros buscando .centro-desarrollo.json.
2. Si no aparece, buscar en carpetas hijas y hermanas hasta profundidad 2,
   SIN asumir el nombre de la carpeta del centro.
3. <HUB> = dirname(marcador);  <ROOT> = normpath(<HUB>/codigo.root_rel)
4. Si no aparece: PREGUNTAR la ruta al usuario. Nunca inventarla.
```

El paso 4 no es un detalle de cortesía: un agente que adivina la ruta del centro escribe artefactos
en un sitio equivocado y el fallo se descubre días después, cuando el tablero lleva una semana
mintiendo.

**Comprobación rápida de que el marcador está bien:**

```bash
python3 .claude/skills/_lib/centro_lib.py --info
```

## 1. Claves de identidad

| Clave | Tipo | Obligatoria | Qué es |
|---|---|---|---|
| `centro` | texto | sí | Nombre humano del centro. **Documental**: aparece en el tablero y en los reportes; nadie decide nada con él. |
| `formato` | texto | sí | Versión del **esquema de este archivo**, no del centro ni del proyecto. Sirve para saber contra qué contrato se escribieron las skills que lo leen. Se sube cuando se añade o cambia una clave. |
| `descripcion` | texto | recomendada | Autodocumentación del archivo: qué es y cómo se localiza. Es lo primero que lee quien abre el marcador sin contexto. |

## 2. `paths` — rutas internas, todas relativas a `<HUB>`

```json
"paths": { "hub": ".", "docs": "docs", "index": "docs/index.md", "...": "..." }
```

| Clave | Por defecto | Para qué |
|---|---|---|
| `hub` | `.` | El propio centro. |
| `docs` | `docs` | La biblioteca de patrones (**el insumo**). |
| `index` | `docs/index.md` | El **dispatcher**: la tabla «Cargar cuando…» con la que se selecciona contexto. |
| `arquitectura` | `docs/arquitectura-general.md` | La puerta de entrada del insumo. |
| `lecciones` | `docs/lecciones.md` | Memoria de proceso, append-only. |
| `decisiones` | `docs/decisiones` | ADRs. Capa **opcional**. |
| `work` | `.work` | El trabajo: un directorio por funcionalidad. |
| `skills` | `.claude/skills` | El método. |
| `config` | `.claude/config-proyecto.md` | Los parámetros del proyecto. |
| `sitio` | `centro-desarrollo` | Salida **generada** del tablero. Desechable: se borra y se regenera. |
| `paginas` | `paginas` | Markdown **fuente** de las páginas narrativas del sitio. Vive **fuera** de `sitio` porque el render borra y regenera `sitio` entero: dentro se perdería en la primera pasada. |
| `recursos` | `resources` | Material crudo de extracción. Interno, no autoritativo. |

**Se pueden omitir**: `centro_lib.py` aplica estos valores por defecto, así que un marcador incompleto
no rompe. Declararlas igualmente es barato y hace el archivo legible sin consultar el código.

> **Advertencia de honestidad.** En el centro maduro del que sale esta guía, `paths` **es
> decorativo**: nadie lo resuelve y las rutas están escritas literalmente dentro de las skills, así
> que cambiar un valor ahí no mueve nada. Aquí sí es real —`centro_lib.ruta("docs")` lo resuelve—
> **con una condición: que las skills usen `centro_lib` y no reescriban rutas a mano.** Si en tu
> centro alguna skill vuelve a cablear `docs/`, esta clave vuelve a mentir. Un contrato que miente es
> peor que no tenerlo, porque alguien lo cambiará confiando en que surta efecto.

## 3. `docs.slices` — cómo se parte la biblioteca de patrones

```json
"docs": { "slices": ["back", "front"] }
```

Un **slice** es una subcarpeta de `docs/` con sus propios patrones numerados. La partición típica es
por capa tecnológica, porque es la que hace que un patrón tenga un solo dueño y una sola numeración.

- **Un solo slice es perfectamente válido** (`["src"]`, `["app"]`): un monolito no necesita fingir
  que tiene dos lados. La numeración `NN` es única **dentro** de cada slice.
- Los nombres de slice se usan además en `codigo.repos.<alias>.slice`, para saber qué patrones
  aplican a qué repositorio.
- Añadir un slice después es fácil (una carpeta y una sección en el índice). **Renombrarlo no lo es**:
  rompe los enlaces del índice y todas las referencias cruzadas de los patrones.

## 4. `codigo` — cómo se llega del centro al código

```json
"codigo": {
  "root_rel": "..",
  "repos": {
    "api": { "ruta": "backend",  "slice": "back",  "desc": "API HTTP" },
    "web": { "ruta": "frontend", "slice": "front", "desc": "Aplicación de cliente" }
  }
}
```

| Clave | Qué es |
|---|---|
| `root_rel` | Ruta relativa **desde `<HUB>` hasta `<ROOT>`**. `".."` si el centro es hermano del código; `"."` si el centro **es** la raíz; `"../.."` si cuelga dos niveles. |
| `repos` | Diccionario **alias → dónde está**. El alias es el nombre corto con el que el resto del centro se refiere a ese código (en `workspaces`, en la configuración, en los artefactos de un item). |
| `repos.<alias>.ruta` | Ruta relativa desde `<ROOT>`. Puede ser multi-segmento (`servicios/api`) y puede ser `"."` cuando el repositorio **es** la raíz. |
| `repos.<alias>.slice` | Qué slice de `docs/` documenta ese código. Opcional pero útil: es lo que permite decir «para tocar `api`, mira los patrones de `back`». |
| `repos.<alias>.desc` | Descripción humana. Aparece en reportes. |

**Los tres layouts que cubre este esquema** (y es a propósito que sean tres y no dos):

| Layout | `root_rel` | `repos` |
|---|---|---|
| Un solo repositorio, el centro dentro (`<repo>/development-hub/`) | `".."` | `{ "app": { "ruta": "." } }` |
| Un solo repositorio con dos carpetas dentro | `".."` | `{ "api": {"ruta":"backend"}, "web": {"ruta":"frontend"} }` |
| Varios repositorios hermanos, centro hermano también | `".."` | `{ "api": {"ruta":"servicios/api"}, "web": {"ruta":"clientes/web"} }` |

> **Por qué un diccionario de alias y no `back` + `front`.** El esquema del centro de referencia
> asume exactamente dos familias de repositorios en dos carpetas contenedoras. **Un proyecto de un
> solo repositorio no cabe en ese esquema, y es el caso más común.** Con alias, un monorepo se
> declara con un único repo de `ruta: "."` y todo lo demás del centro sigue funcionando igual.

## 5. `workspaces` — el primer nivel del trabajo y del tablero

```json
"workspaces": {
  "producto": { "repos": ["api", "web"], "desc": "Producto (único workspace)" }
}
```

| Clave | Qué es |
|---|---|
| `<nombre>` | Es el primer nivel de `.work/` (`.work/<workspace>/<item>/`) y una página del tablero. |
| `repos` | **Lista de alias** de `codigo.repos`. Es lo que la guardia de rama usa para saber en qué repositorios tiene que verificar y crear la rama de trabajo. |
| `desc` | Descripción humana. **La consume el generador del sitio** para titular la página del workspace: si falta, la página se titula con el nombre técnico. |

**Qué es un workspace:** una **unidad de reporte** —lo que un responsable quiere mirar por
separado— y a la vez el puntero a los repositorios donde se implementa.

**Qué NO es:** una capa técnica. Partir en `back`/`front` es un error, porque una funcionalidad casi
siempre cruza ambos y quedaría partida en dos items que nunca cierran a la vez. Criterios sanos:
área de negocio, módulo funcional, producto o cliente.

**El caso de un solo workspace es legítimo y será el más común.** Todo el mecanismo funciona igual
con una sola fila en las tablas. No inventes workspaces para que el tablero se vea más lleno: un
workspace que nadie consulta por separado es ruido.

> **Cuidado con las listas que no son listas.** En el centro de referencia, un workspace declara su
> frontend como `"front-module-apollo · front-module-common"`: eso **no es una ruta**, es una
> descripción, y cualquier código que intente resolverla se rompe. Por eso aquí `repos` es una lista
> de alias y no texto libre. Si un workspace toca tres repositorios, se ponen los tres alias.

## 6. `git` — la política de ramas, declarada una sola vez

```json
"git": {
  "principales": ["main"],
  "base_por_defecto": "main",
  "convencion_rama": "<tipo>/<TICKET>-<slug>"
}
```

| Clave | Qué es |
|---|---|
| `principales` | Ramas a las que **nunca** se commitea directo. La guardia de rama para y pregunta si detecta que se está en una de ellas. Un equipo con varios ambientes pone aquí todas: `["main","staging","uat"]`. |
| `base_por_defecto` | Rama desde la que se crean las ramas de trabajo. |
| `convencion_rama` | Formato del nombre de rama. Documental pero citado por la forja y por la skill de commit. |

Está en el marcador —y no dentro de las skills— porque cablearlo en las skills es exactamente lo que
hace que un centro copiado a otro proyecto ramifique desde `master` en un equipo que usa `main`.

## 7. `doctor` — el chequeo de integridad se configura, no se cablea

```json
"doctor": {
  "skills_requeridas": ["centro", "forjar-skill", "desarrollar", "casos-prueba", "centro-doctor"],
  "config_secciones": [1, 2, 3, 5, 7, 9, 10, 13, 17, 18, 21],
  "min_patrones": 0
}
```

| Clave | Qué es |
|---|---|
| `skills_requeridas` | Qué skills tienen que existir con frontmatter válido. **Es también el manifiesto del centro**: de aquí deberían leer la puerta de entrada, el instalador y la página de skills del tablero, en vez de tener cada uno su propia lista. **Van con el prefijo del proyecto** (`miproducto-centro`, `miproducto-forjar-skill`…): el directorio global de skills es compartido y sin prefijo un centro pisa a otro en silencio. Actualiza esta lista **en el mismo cambio** en que renombres las skills. |
| `config_secciones` | Qué secciones de `.claude/config-proyecto.md` tienen que existir. Las skills las citan por número, así que su ausencia rompe citas en silencio. Incluye aquí **toda sección que una skill lea para estampar algo**, aunque la guía la marque opcional: §4 (perfiles) alimenta el bloque `## Rol` del playbook. |
| `min_patrones` | Mínimo de patrones esperado. **Empieza en `0`** y se sube conforme la biblioteca crece. |

> **Por qué configurable.** En el centro de referencia estos valores están cableados dentro del
> chequeo (una lista de catorce skills, «al menos 26 patrones de un lado y 32 del otro»), con dos
> consecuencias: un centro recién montado **parece enfermo sin estarlo**, y las listas ya divergen
> entre los cuatro archivos que las repiten. Un chequeo que está siempre amarillo deja de leerse en
> dos semanas.

## 8. Errores frecuentes al rellenarlo

| Síntoma | Causa habitual |
|---|---|
| «No se encontró el marcador» desde un repo de código | El centro no es ancestro del directorio de trabajo y no se corrió la instalación de skills. |
| Un repo aparece como `NO EXISTE` en `--info` | `root_rel` o `repos.<alias>.ruta` no coinciden con el disco **de esa máquina** → va en `.centro-desarrollo.local.json`, no en el marcador compartido. |
| Los items de un workspace no salen en el tablero | El workspace no está declarado aquí. El descubrimiento solo recorre los declarados. |
| El doctor exige una skill que no vas a escribir | Quítala de `doctor.skills_requeridas`. La lista es tuya, no una herencia. |
| El tablero titula la página con el nombre técnico | Falta `desc` en ese workspace. |

---

## 9. Qué **no** puede ir en el marcador

- **Rutas absolutas.** Todo es relativo a `<HUB>` o a `<ROOT>`; el marcador se versiona y viaja a
  otras máquinas.
- **El layout de código de una máquina concreta.** Eso es `.centro-desarrollo.local.json`
  (gitignored, con precedencia). Ver `.centro-desarrollo.local.example.json`.
- **Política de trabajo, comandos, umbrales, definición de terminado.** Eso es
  `.claude/config-proyecto.md`. El marcador declara **dónde están las cosas**; la configuración
  declara **cómo se trabaja**.
- **Secretos, credenciales o URLs de entornos.** Nada de eso hace falta para localizar el centro.
